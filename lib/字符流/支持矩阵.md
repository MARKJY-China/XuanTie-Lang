# 支持矩阵 —— TUI 库化的平台与运行时承诺

> 目的：本库的字符界面（TUI）能力提取自一个真实运行的全屏音乐播放器应用，
> 现作为通用 TUI 库贡献给玄铁。本文档提前声明"支持的版本"——系统版本、
> 依赖版本、终端能力——避免未来使用者在不受支持的环境上踩雷
> （1607/1709 老系统踩雷是本矩阵的直接动因）。
> 定稿于 2026-11-08，结论由来源应用一方讨论定案。

## 0. 支持的定义

**受支持环境 = 维护者接受并处理 issue 的范围。**

在受支持环境内报告的问题会响应与修复；在明确不支持的环境内的问题，
issue 会被引导至对应的替代方案（如"请安装 Windows Terminal"）后关闭。
**声明支持的范围 = 实际测试验证过的范围**，没有测试机的环境不声明
（宁可窄而诚实，不宽而空头）。

## 1. VT 序列——为什么"支持的终端版本"是命根子

程序与终端之间只传字节流，双方约定：`ESC`（0x1B）开头的字节段是给终端
执行的指令（VT/ANSI 转义序列），其余字节直接显示。程序画成什么样，
取决于终端认识多少指令。

本库实际使用的序列（程序 → 终端，渲染指令）：

| 序列 | 效果 |
|---|---|
| `ESC[48;5;24m` / `ESC[38;5;Nm` | 256 色前景/背景（头栏蓝底、配色） |
| `ESC[2J` / `ESC[H` | 清屏 / 光标回原点 |
| `ESC[?1049h` / `ESC[?1049l` | 进/出备用屏（退出不毁用户终端） |
| `ESC[?1000h` `ESC[?1006h` | 开启鼠标上报（X10/SGR S-ext 模式） |

反向（终端 → 程序，事件编码）：

| 序列 | 含义 |
|---|---|
| `ESC[<0;500;3M` / `…m` | SGR 鼠标：第 500 列第 3 行左键按下/释放 |
| `ESC[<64;C;RM` / `ESC[<65;C;RM` | 滚轮上/下 |
| `ESC[A` `ESC[B` `ESC[C` `ESC[D` | 方向键 |

终端不认识某条指令的后果：256 色不认识 → 只剩黑白反显；SGR 鼠标
不认识 → 点击/滚轮无反应；备用屏不认识 → 退出后毁掉用户终端内容。
**这就是"支持的终端/系统版本"必须显式声明的原因。**

## 2. Windows 三件套沿革与支持线

时间顺序：conhost（2009，Win7）→ winpty（2015~2016，社区）→ ConPTY（2018，官方）。

- **conhost**：Windows 自带终端本体（CMD/PowerShell 5.1 弹出的那个窗口），
  Win7 起从 CSRSS 拆出独立存在。VT 序列支持自 Win10 1607 起逐步补全，
  但鼠标/备用屏等细节在 1809 时代仍残缺，渲染观感老旧。
- **winpty**：第三方项目（rprichard）。微软当时没有伪终端 API，git-bash/mintty
  等 Unix 风格终端拿不到 pty，winpty 用"隐藏 conhost + 桥接翻译"硬实现，
  代价是宽度截断等转换损耗（"每行字符限制"的时代来源）。
- **ConPTY**（Pseudo Console）：微软官方伪控制台 API（Win10 1809 / build 17763），
  把 winpty 的思路转正。它不是程序也不是窗口，是一层"VT 字节流 ↔ Console API"
  的翻译管线；Windows Terminal 即通过 ConPTY 托管 shell。winpty 从此退役。

**支持线定为 Win10 1903（build 18362）+ Windows Terminal**，理由：

1. Windows Terminal 的官方最低系统要求就是 1903——它是 Windows 上 VT
   支持最完整的终端，本库依赖的全部终端能力（256 色、SGR 鼠标、备用屏）
   只有在它上面才完整可用；
2. ConPTY 首发年（1809）的已知缺陷（宽字符、resize）在 1903 修了一批；
3. conhost 的 VT 支持到这个节点才基本可用；
4. Win10 已于 2025-10 停止支持，为老版本投入测试不划算；但 Win10 仍可
   安装 Windows Terminal，"装了 WT 的 Win10"与 Win11 同等受支持。

**义务边界**：受支持环境内的问题接受 issue 并修复。支持基准向 Win11
看齐——Windows Terminal 已是 Win11 的内置默认终端；Win10 降为备选项：
网吧等场景仍在用、绕不开，好在 WT 可手动安装。口径只有一条——
**有 WT 管，没 WT 不管**：Win11 内置 WT 管；Win10 装了 WT 管；Win10
没装 WT、系统默认弹出的终端窗口不管——裸 conhost 渲染老旧：中文
环境默认宋体、字形覆盖残缺（连 ✓ 这类常用符号都渲染不出），TUI
需要的鼠标上报等终端能力也不完整；Win10 又已于 2025-10 停更，
为它投入支持不划算。1607/1709 及更早（winpty 时代）同样明确不支持。

## 3. OS 支持矩阵

| OS | 基准终端 | 支持口径 |
|---|---|---|
| macOS | Terminal.app / iTerm2 / WezTerm 等，版本无需区分 | **全功能**（tty 传输、键鼠事件、序列全可用）。实测基线 macOS 26；更老版本未测不声明 |
| Linux | 各主流终端（GNOME Terminal/Konsole/alacritty/kitty 等）无需区分，VT 实现完整、无版本线 | 全功能；tmux/screen 内运行为已知降级场景（鼠标协议可能被拦截） |
| Windows | **Windows Terminal**（Win11 内置 / Win10 1903+ 手装） | 按 WT 能力声明全部特性（需第二条读键路径，见 §6，当前未实现）；未装 WT 的默认终端窗口（裸 conhost）明确不支持；1607/1709 及更早明确不支持 |

Unix 侧不需要版本线的原因：各主流终端都完整实现了 VT/xterm 约定，
碎片化不在终端本体，只在 tmux/screen、ssh 无 ctty 等**场景**（属降级
声明，不分版本）。Windows 侧必须区分的原因：VT 支持随系统版本差异巨大
（1607→1809→1903 三道分水岭），且老系统真实存在（踩过雷）——样本来自
「挂机宝」类远程 Windows 主机：自称 Win10、实为 1607 年代旧版本，
怪问题频出。网吧不是老系统来源：主流网吧机就是新近的 Win10（实测样机
22H2 / build 19045，硬件配置并不旧），但系统普遍把 Microsoft Store
精简掉了（开始菜单无此项，组件拉起也弹不出窗口或直接报错），Windows
Terminal 只能走命令行安装——从 GitHub 发行页下载 msixbundle 后以
PowerShell `Add-AppxPackage` 装入，或经 winget 安装（无 GUI 安装程序）——
实测网吧样机上跑的 WT 就是这么装上的。

## 4. 玄铁运行时最低版本：26.11.3

本库依赖以下运行时能力/语义，缺一则轮询读键路径失效：

| 依赖 | 用途 | 语义约定（比"函数存在"更关键） |
|---|---|---|
| `文件.打开(路径, "读")` | tty 轮询读键 | 模式是中文「读」；返回 Result 须 `.值` 后调句柄方法 |
| `句柄.读字节(n)` | 每拍读 1 字节 | **超时空读返回"成功且空串"**，不是失败——只判 `.成功` 会导致句柄永不关闭、粘性 EOF 卡死全部输入 |
| `句柄.关闭()` | 空读弃句柄 | stdio 缓冲：句柄常驻才能不丢多字节序列（鼠标/方向键），空读才弃 |
| `时.毫秒()` / `时.微秒()` | 协议目录唯一命名 | — |
| `stty raw -echo min 0 time 1` | 读自带 100ms 超时 | Unix 命令依赖；`/dev/tty` 设备文件依赖（Windows 无，见 §6） |

已知不依赖（不必声明）：`选()`/通道（主线程泵送 gate 未解 #142，无限读键任务
会卡死主线程，见 docs/异步任务环境隔离-实验报告 与 踩坑-玄铁语言实现备忘）。

## 5. 终端能力分级与降级行为

| 级别 | 能力 | 缺失时的降级 |
|---|---|---|
| 必需 | VT100 基础序列 + 备用屏 + 逐字节读 | 无法工作，明确报错退出 |
| 增强 A | 256 色 SGR | 降级黑白反显，功能不损 |
| 增强 B | SGR/X10 鼠标上报 | 失去鼠标/滚轮，键盘路径完整 |

库化时应提供启动自检：探测运行时语义（§4）与 tty 能力，不满足时明确
报告缺什么，而不是静默怪异。

## 6. Windows 化预留（未实现，方向备忘）

当前读键路径有三个硬 Unix 依赖：`stty`、`/dev/tty`、POSIX 信号语义的
Ctrl+C——Windows 上全部不存在。Windows 化 = 第二条读键/渲染路径 +
抽象层，按"程序说 VT、ConPTY 承诺完整翻译"的基准设计：

- 读键：ConPTY 输入流或 `ReadConsoleInput` 事件模型（替代 stty 轮询）
- 渲染：同一套 VT 序列输出，WT 完整解释
- 底线：Win10 1903+；不做 winpty 兼容层

  （`tui_mouse_check.py` / `tui_idle_refresh_check.py` / `tui_selection_follow_check.py`）

## 8. 贡献形态决议（2026-11-08 定案）

**音频「出声」域不贡献**——本库来源于一个音乐播放器应用，应用里的
音频播放、系统托盘、媒体键、正在播放（Now Playing）等平台集成能力
与字符界面毫无关系，全部留在应用侧，不属于本库。

**库的边界 = 底层字符/事件传输层**（踩过坑的地方），只沉淀这些：

进库（底层，坑的沉淀）：

| 能力 | 沉淀的坑 |
|---|---|
| tty 原始模式管理（stty raw -echo min 0 time 1、退出恢复） | VTIME 读超时；忘恢复终端残留 raw 模式 |
| tty 轮询读键（/dev/tty 句柄常驻 + 空读即弃） | stdio 缓冲吞多字节序列（只剩孤 ESC，鼠标全灭）；粘性 EOF；超时空读返回"成功且空串" |
| ESC 序列消歧（单 ESC 键 / 方向键 / SGR 鼠标 / X10 鼠标） | 阻塞读后续字节导致的挂死与误判 |
| 事件抽象：键事件 / 鼠标事件（按下/释放/滚轮/坐标） | 终端→程序的输入编码（SGR 1006、X10）解析 |
| 显示宽/裁宽/补齐宽（按码点判宽） | 全部多字节一律计 2 → ▓░♪▶ 等单列字符虚增宽度，头栏截断过早+大空白（真机踩坑） |
| 色码辅助：前色(n)/背色(n) + "先纯文本定宽、拼接时包裹色码"约定 | 色码不占列但会被宽度函数当字符计宽——约定比函数重要 |

不进库（应用层，一人一个样）：

- 列表交互、标题栏、底部按键栏、搜索框等布局与交互实现
- 配色方案（哪个界面什么颜色——应用自己定；库只给色码原语）
- 播放管理、音频播放与系统媒体集成、跨进程协议文件目录（本应用放在 /private/tmp，属应用实现细节）
- 窗口尺寸管理策略（stty size 读取可进库，重绘策略属应用）

库的接口形态即"字符怎么传过来、键盘/鼠标事件怎么给"：初始化（进备用屏
+ raw 模式 + 鼠标协议开关）→ 每拍 `取事件()` 返回 键/鼠标/空转心跳 →
退出（恢复终端）。应用拿事件流自己组织界面。

Windows 化（§6）随之归属库层：ConPTY 读键路径是库的未来工作项。

## 9. 坑的稳定性模型与已知雷区

坑不是一次性踩完的。按根源分三类，库文档应分开记录、分开维护：

**第一类：已验证坑（协议层，基本永不过期）**——根源在协议与系统行为本身
（VT/ANSI 约定、stdio 缓冲、代码签名机制），协议不变坑就不变。§8 表格
里的全部条目属于此类，是库的价值底盘。

**第二类：运行时版本绑定坑（会随玄铁版本消失或新增）**——根源在玄铁运行时
的 bug/语义缺口：`收` 超时参数被整体丢弃（收(0)/收(3000) 空道均挂死，#143）、主线程泵送 gate（#142）、深层嵌套失效、
"成功且空串"语义。每条必须标注发现时的运行时版本（26.11.3），运行时
更新后复核划掉（如 26.11.08 修了 时.睡 整数毫秒）。

**第三类：已知雷区（未踩过、有明确预判，待应用撞上后验证转正）**——
不是坑不存在，是本应用功能没用到位所以还没触发。预判如下：

| 雷区 | 预判机制 | 玄铁现状 |
|---|---|---|
| 窗口 resize 重绘 | 需要 SIGWINCH 信号，收不到就不知道终端变了尺寸 | 运行时大概率无信号处理能力，只能轮询 stty size 对比 |
| 双宽字符中间截断 | 裁宽若在 CJK 字符字节中间切，输出乱码 | tui.裁宽 按字符遍历应安全，但边缘未测 |
| 组合字符/emoji/零宽字符 | 宽度判定全错（U+200D、变体选择符、软键盘 emoji） | 字符宽() 未处理，真撞上再定策略 |
| 粘贴多行进输入框 | 括号粘贴模式（bracketed paste）未启用时，换行被当回车执行 | 未启用 2004h，搜索框只收单行可暂时规避 |
| tmux/screen 内鼠标协议 | tmux 不开 mouse 选项时 SGR 不转发 | §3 已声明为降级场景 |
| 终端缩放/字号变化后的残影 | 尺寸变化未触发全量重绘 | 同 resize 雷区 |
| 大列表逐行重绘性能 | 全帧重绘在千行列表上的耗时 | 261 首无感知，千行级未测 |

雷区的处理原则：**应用撞上 → 复现脚本 + 字节级定位 → 转正为第一/二类坑**。
这个"转正"动作就是库文档的日常维护方式，也是 community 补充文档的入口。

## 10. 贡献定案：库名、范围、形态、流程（2026-11-08 讨论）

### 10.1 库名：字符流

- **名称 = `字符流`**，简介 = "字符界面（TUI）底层库：tty 传输、键盘鼠标事件、
  转义序列编码解码。管字符进出，不管界面长相。"
- 淘汰记录（免得将来重新争论）：tty（会让人联想 Linux 内核贫瘠控制台——虽
  广义 tty=终端设备，但第一印象劝退）、终端（易误解为终端模拟器）、TUI/字符
  界面（引发"管我界面"的错误期待）、管道（撞 shell 竖线）、底座（抽象）、
  事件（只覆盖读不覆盖写）。
- **硬纪律：库的名称、简介、文档一律不出现 CLI 字样**——本库面向"给人看的
  字符界面"，与命令行工具的实现是两个世界。
- 为什么"同源却分受众"：CLI 也跑在字符流上（stdin/stdout），但只用最表层——
  熟模式（内核攒行、回车交付）+ 纯文字。TUI 用的是整个地基：raw 模式逐字节、
  转义序列、事件级输入。两者无墙，是一个连续谱：**用转义序列控制终端的深度**。
  CLI 的 `\r` 原地重绘进度条就是滑向 TUI 的第一级台阶（控制光标 → 发色码 →
  要多区域布局 → 要 raw 模式响应按键，每一步都"只是高级一点点"）。库服务
  走进连续谱深处的人；简介不提 CLI 是划受众，不是否认技术同源。

### 10.2 贡献范围（最终版）

进库五件（第一档，全部真机验证过）：

1. tty 模式管理（进备用屏 + stty raw -echo min 0 time 1 + 退出恢复）
2. tty 轮询读键（/dev/tty 句柄常驻 + 空读即弃 + "成功且空串"处理）
3. ESC 序列消歧状态机
4. SGR 鼠标（1006）解析 → 事件结构
5. 坑文档（本文档 §8 已验证坑 + §9 已知雷区）

待办一件：X10 鼠标解析——代码在但从未被真实触发，补 pty 测试后转正。

**不进**：判宽/裁宽/补齐宽（东亚宽度是数万行码点表，现有实现是近似子集，
`—`/`♪` 属 Ambiguous 类终端间不一致，将来必然要改，不符合"稳固无可改"标准）；
音频播放与系统媒体集成（出声域）；一切应用层（§8 清单）。

### 10.3 物理形态：tiepm 包

照官方库体例（考古样本：lib/数组、lib/UI、lib/渲染）：

```
lib/字符流/
├── tiepm.toml      # [包]名称/版本/仓库/作者 [描述]简介/许可 [依赖]#无
├── 字符流.xt        # 公 函 导出 / _ 前缀私有 / 函数带参数返回文档注释（照官方格式）
├── changelog.md
├── 支持矩阵.md      # 本文档随库走
└── 测试/            # Python pty 套件 + 三专项（已定：测试资产随库走，
                    #  Python 只是实现，语言可换；"声明=测过"需要测试在场）
```

语言层约定（官方实拍）：使用方 `引 "字符流" 予 流` 后以 `流.取键节()` 前缀
调用；`公 函`/`公 常` 导出，无 `公` 为私有；运行时 C 函数用
`外 函 xt_xxx(): 类型` 声明。
