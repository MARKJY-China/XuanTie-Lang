# 发布通道与升级源（issue #163）

> 目标：`xtc 升级` 支持 **stable / dev 双通道**、支持 **钉版本/回滚**，并且不再依赖系统 `curl`
> —— 清单走语言内建 `求()`，发行包 `tar.gz` 走运行时二进制 HTTP，Windows 裸机也能升级。

## 1. 分支 → 通道 → 清单（四分支口径）

| 分支 | 通道 | 清单文件 | 说明 |
|---|---|---|---|
| `develop` | `dev` | `latest-dev.json` | 每次 push 滚动构建；dev 清单只由 `dev.yml` 写，**绝不覆盖** `latest.json` |
| `master` | `rc` | `latest-rc.json`（v1.0.0 起） | 当前预发布阶段 `release.yml` 仍按 stable 通道写 `latest.json`；rc 由版本串自述（`-V` 显示 `通道=rc`） |
| `stable` | `stable` | `latest.json` | 正式稳定版；非 dev 的旧消费方仍读它 |
| `hotfix` | — | 不单独出清单 | P0 热修短分支，修完合回 `stable` 并同步 `master`，随后打 `v1.0.x` tag 走 stable 通道 |

`xtc 升级 --通道` 只接受 `stable` / `dev` 两个值（`rc` 是版本串的通道自述，不是 `--通道` 的取值）。

## 2. 数据流

```
                ┌── release.yml(v* tag) ──▶ latest.json / latest-rc.json ─┐
发布产物 ────────┤                                                         ├──▶ dump 到 ROS 桶根
                └── dev.yml(push develop) ─▶ latest-dev.json ─────────────┘
                                                    │
                文档站 nginx 反代/重定向  /api/latest.json、/api/latest-dev.json
                                                    │
                                                    ▼
                                        xtc 升级 [--通道 stable|dev]
```

清单地址默认：

- stable：`https://xuantie.markjy.com/api/latest.json`
- dev：`https://xuantie.markjy.com/api/latest-dev.json`（由 stable 源把文件名 `latest.json` 换成 `latest-dev.json` 派生；`--源` 覆盖的 stable 源同样按此规则派生）

## 3. 清单结构（两种通道同构）

```json
{
  "channel": "stable",                 // stable | dev（rc 清单同构）
  "version": "v1.0-rc.4-20261119.1",   // 本清单指向的版本号
  "commit": "07318640472ad4483ea3d8371a14e108c470c2d1",
  "date": "2026-11-19",
  "notes_url": "https://github.com/MARKJY-China/XuanTie-Lang/releases/tag/<tag>",
  "tag": "v1.0-rc.4-20261119.1",       // 发布 tag；dev 通道固定为 "dev"
  "published_at": "2026-11-19T00:00:00Z",
  "assets":    { "windows_amd64": { "url": "https://…/xuantie_<tag>_windows_amd64.tar.gz", "sha256": "…", "size": 63286234 } },
  "platforms": { "…与 assets 完全相同（兼容旧版 xtc 升级）…" },
  "manifests": { "windows_amd64": { "url": "…", "sha256": "…", "size": 0 } }
}
```

- 平台键固定：`windows_amd64` / `windows_arm64` / `linux_x86_64` / `linux_arm64` / `darwin_arm64`。
  清单允许缺平台键（dev 通道当前只构建部分平台），客户端缺自身平台键时**明确报错**、不崩。
- 版本号形态：正式/rc 为 `v<编译器版本>-<YYYYMMDD>.<序号>`；dev 为 `v<编译器版本>-dev.<YYYYMMDD>.<sha7>`。
- `xtc` 读取口径：版本取 `version`（缺失回退 `tag`）；平台资产**优先 `assets`，回退 `platforms`**（条目是
  `{url,size,…}` 字典；防御性也接受纯 url 字符串）；`commit` 用于升级后自检；`size` 用于下载字节数校验。
- 清单详细字段/落盘/保留策略以发布基础设施文档为准：见 [`release/RELEASE_README.md`](../release/RELEASE_README.md)。

## 4. `xtc 升级` 行为

```bash
xtc 升级                                  # 默认 stable：读 latest.json，装最新稳定版
xtc 升级 --通道 dev                       # dev 通道：读 latest-dev.json（首次从非 dev 版本切过去会打印警告）
xtc 升级 --检查                           # 只查更新，不下载安装
xtc 升级 --检查 --通道 dev                # 查 dev 通道
xtc 升级 --版本 v1.0-rc.4                 # 钉版本/回滚：绕过清单，直接下载该 tag 的发行资产
xtc 升级 --版本 v1.0-rc.4 --国内          # 钉版本改走 Gitee 镜像（GitHub 不可达时用）
xtc 升级 --强制                           # 同版本/同提交也强制重装
xtc 升级 --目录 <dir>                     # 指定安装目录（默认编译器自身目录；空目录按全新安装）
xtc 升级 --源 <url>                       # 覆盖 stable 清单地址（dev 按同目录 latest-dev.json 派生）
```

细节：

- **通道**：默认 stable；`--通道 dev` 首次切换（当前运行版本串不含 `-dev`）会明确警告“开发预览版”。
  rc 不作为升级通道参数，rc 版本由 `-V` 的版本串自述。
- **钉版本/回滚**：`--版本 <tag>` 跳过清单，按 `xuantie_<tag>_<平台>.tar.gz` 从 GitHub release 下载
  （`--国内` 时走 Gitee 镜像）。只对 stable/rc 的正式 tag 有效——dev 资产名随构建日期变化，
  `--版本 <dev 版本>` 会明确报错并提示改用 `--通道 dev`。
- **清单网络**：`求(地址)`（运行时 HTTP；支持 https/proxy/重定向/chunked），**不再调用系统 `curl`**。
- **发行包下载**：运行时新增 `xt_http_get_bytes`（`runtime/xt_net.c`）——与 `求()` 共用同一套
  重定向/chunked/代理/TLS 实现，但保留**正文真实字节长度**（二进制安全，可含 NUL），失败/空正文明确报错。
- **安装前校验**（任一步失败都保留原安装目录，不静默覆盖）：
  1. HTTP 非 2xx、0 字节正文 → 报错；
  2. gzip 魔数不符（`1F 8B`）→ 报错；
  3. 清单带 `size` 时字节数必须一致；
  4. 解压出的 `xtc` 必须存在；
  5. 跑解压出的 `xtc -V` 自检：清单带 `commit` 时按提交哈希核对，否则按版本串双向核对
     （发布 tag 与二进制自述都包含完整日期/序号，版本常量在打 tag 前已改为完整 tag）。
- **已是最新**：目标版本等于当前版本，或清单 `commit` 等于当前包 `MANIFEST.txt` 的提交时跳过（`--强制` 除外）。

## 5. `xtc -V`：版本 + 通道 + 提交

```text
$ xtc -V
玄铁 (XuanTie) 编译器驱动 v1.0-rc.5 通道=rc 提交=07318640472ad4483ea3d8371a14e108c470c2d1
```

- 通道按版本串后缀判定：含 `-dev` → `dev`；含 `-rc` → `rc`；其余 `stable`。
- 提交读发行包 `MANIFEST.txt` 的 `提交: <hash>` 行（与 `-h` 打印的「编译器自述」同源）；
  裸可执行文件/无清单时输出 `提交=unknown`，不猜。
- `-h` 首行保持旧格式（`玄铁 (XuanTie) 编译器驱动 <版本>`）以兼容既有工具，仅在其后追加一行通道/提交。
  报 bug 请附 `-V` 这一行。

## 6. 发版（基础设施侧）

- 发布清单由 `tools/publish-ros.mjs` 生成并上传：`--channel stable|dev|rc` 分别写
  `latest.json` / `latest-dev.json` / `latest-rc.json`（v1.0.0 前 rc 走 stable 通道，行为与现状一致）。
- 流程、目录约定、保留策略详见 [`release/RELEASE_README.md`](../release/RELEASE_README.md)。

```bash
# 参考（真实参数以发布基础设施文档为准）
node tools/publish-ros.mjs --dir artifacts --version "$TAG" --channel stable
node tools/publish-ros.mjs --dir artifacts --version "$DEV_VERSION" --channel dev
```

## 7. 一次性配置

1. 雨云 ROS 建桶（建议公开读）；记下 endpoint、桶名、AccessKey/SecretKey。
2. 绑定公开域名（或直接用 `https://<桶名>.<endpoint>`），CI 里配：

| Secret | 说明 |
|---|---|
| `ROS_ENDPOINT` | 例如 `https://cn-sy1.rains3.com` |
| `ROS_BUCKET` | 桶名 |
| `ROS_ACCESS_KEY` | 雨云 AccessKey |
| `ROS_SECRET_KEY` | 雨云 SecretKey |
| `ROS_PUBLIC_BASE` | 公网前缀，例如 `https://download.xt.markjy.com` |

3. 文档站 nginx 加两条（两条都要，dev 通道依赖第二条）：

```nginx
# A. 重定向到 ROS 上的清单（最简单）
location = /api/latest.json {
    return 302 https://download.xt.markjy.com/latest.json;
}
location = /api/latest-dev.json {
    return 302 https://download.xt.markjy.com/latest-dev.json;
}

# B. 或反代（隐藏 ROS 域名）
location = /api/latest.json {
    proxy_pass https://download.xt.markjy.com/latest.json;
    proxy_set_header Host download.xt.markjy.com;
}
location = /api/latest-dev.json {
    proxy_pass https://download.xt.markjy.com/latest-dev.json;
    proxy_set_header Host download.xt.markjy.com;
}
```

## 8. 兼容性说明

- 旧版只有 `platforms` 的 `latest.json`（如 v1.0-rc.4）仍可被新版 `xtc 升级` 读取（缺 `assets` 时回退 `platforms`）。
- `xtc 升级 --国内` 保留：清单本身也走文档站；`--国内` 影响钉版本回退下载源（Gitee 镜像），以及缺 url 时的回退地址选择。
- 升级器不再要求系统有 `curl`（Windows 10/11 默认没有 `curl.exe` 的机器也能升级）。
