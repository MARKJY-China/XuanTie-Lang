## 0. 一句话

**当前唯一阻塞 CI 的不是技术，而是"判定依据不在仓库里"**——回归脚本与回归基线都被 `.gitignore` 挡在版本控制之外，任何机器（包括作者换机）都复现不出判定。P0 就是把这个缺口补上并接上 GitHub Actions。

## 2. 阻塞点（报告未点透，但决定 CI 能否落地）

1. **runner 不在仓库**：回归脚本是 `temp/regress.py`，被 `.gitignore:19` 与 `*.py` 规则吃掉；旧 `Test/regression.ps1` 被 `*.ps1` 吃掉 → CI 无脚本可调。
2. **基线不在仓库**：判定模型第 4 层（逐行 diff）读 `temp/regression_golden/`，而 `/temp/` 被整段忽略 → CI 必然 `NO_GOLDEN` 全红。
3. **工具链依赖重**：编译需 `clang -target x86_64-w64-windows-gnu` + MinGW `gcc` + `libraylib.a`；GSC 需 Go。CI runner 上能否装齐、`gcc` 版本是否可用，**需实测**（本地代码注释记载：w64devkit GCC 15.2.0 曾产出无效 exe，故本地优先 TDM-GCC）。
4. **渲染包需预置**：`Test/95_渲染库无窗口API` 等以 `引 "渲染"` 走铁铺解析，CI 上必须先把 `lib/渲染`、`lib/UI` 同步到 `~/.tiepm/已安装/`（即既有"铁铺同步纪律"）。
5. **弹窗类不能进 CI**：96/97/98 会创建窗口，CI 无显示服务 → 必须 `--skip`。
6. **CI 友好度尚可**：110–117 全走 loopback、无外网依赖；`Test/*.xt` 中无 `求()` 调用（不触外部网络）；全量耗时约 13–25 分钟。

## 3. 分阶段方案

### P0 — 判定依据入库 + Windows CI 门禁（本次执行）

**交付物**

| 文件 | 作用 |
|---|---|
| `tools/regress.py` | 从 `temp/regress.py` 抽取的仓库版回归 runner；ROOT 自解析、路径不依赖本机 |
| `Test/golden/*.golden.txt` | 回归基线（从 `temp/regression_golden/` 迁入，随仓库版本化） |
| `tools/bootstrap_check.sh` | 自举链 + DDC 比对脚本：GSC→s1→…→s4，并断言相邻级逐字节一致 |
| `.github/workflows/ci.yml` | 门禁：装 Go/clang/MinGW → 建 GSC → 自举至 s4 → DDC 比对 → 铁铺同步 → 全量回归（跳弹窗类） |
| `.gitignore` 微调 | 放开 `tools/*.py`、`Test/golden/*.txt` 的忽略（用否定规则，不放开全局 `*.py`） |

**门禁判据（四层，缺一即红）**
1. 编译成功性（先删陈旧产物再编，防"编译失败跑旧二进制"假绿）；
2. 进程退出码/超时；
3. 显式 `FAIL` 标记扫描；
4. 与 `Test/golden` 基线逐行 diff（归一化后比对）。

**附加硬门禁**：`s3` 与 `s4` **逐字节一致**（自举固定点），不一致即红。这条把"自举收敛"从一次性动作变成每次提交的机器判据。

**验收标准**：CI 全绿；且**故意破坏一处**（如临时改坏一个测试断言）能让 CI 变红——证明门禁真在判，而不是空转。

**成本**：半天。**风险**：CI runner 上 `clang`/`gcc` 的可得性与版本兼容（本地为 TDM-GCC + clang 22）；若不兼容，退路是锁 runner 镜像或改用 msys2 提供 mingw-w64。

### P1 — 黄金测试集与两级反馈

- 由**作者亲自圈定**黄金集（报告 §3.3.1 明确此项不可委托 AI：测试套件若由 AI 针对 AI 代码生成即构成循环论证）；
- CI 拆两级：黄金集（目标 <5 分钟，每次 push 跑）+ 全量（PR 合并前/定时跑）；
- 黄金集入选者直接复用 `Test/NNN_*.xt`，另建 `Test/golden_manifest.txt` 列出编号，不复制文件（避免两份真源）。

**成本**：1–2 天（其中"圈定"是作者决策，AI 只做执行）。

### P2 — 三平台矩阵

- macOS/Linux 先只跑**核心语法 + 编译器自身**测试（跳渲染类与弹窗类）；
- 前置：macOS 侧需作者实机复验通道条件变量宏的返回语义（PR#16 合并时我们改过该宏，本机无法验证）；
- 渲染类测试在 CI 上长期跳过（无显示服务），改由作者本机实机验收。

**成本**：2–3 天。

### P3 — 治理前置（报告 §5.1.1，成本以天计）

1. 补 `SECURITY.md`（漏洞报告渠道与响应约定）；
2. `lib/渲染/libraylib.a` 治理：补出处与许可说明，或改为发布产物不入库、经铁铺分发；
3. 清理 `lib/渲染/.git` 嵌套仓库残留；
4. 明确 **AI 生成代码披露政策**（报告视其为项目的核心叙事资产，需成文）；
5. 贡献流程书面化（issue/PR 处理约定），为 bus factor=1 解套。

### 明确不做（本期）

- **不重写历史清大文件**（`.git` 231MB、重复字体）：force-push 破坏所有克隆，收益风险比差。替代做法：此后只入源码，发布产物走 GitHub Releases（`release/` 已正确忽略）。
- **不动 `编译.xt` 模块化拆分**（报告 §3.3.2）：那是第二阶段的技术前提，属独立大工程，需先有黄金集仲裁（P1）才可动手。

## 5. 附：CI 门禁的固定命令序列（本地与 CI 共用的真源）

```bash
# 1. 种子编译器
go build -o xt_gsc.exe .

# 2. 自举链：s1 由 GSC 产出，s2..s4 逐级自举（s1 无 -sc 支持，输出名取自源文件基名）
#    注意：GSC 输出名不可为 玄铁.exe（命名纪律），须在独立目录内构建后改名
mkdir -p build
xt_gsc.exe 铁 xuantie_compiler/玄铁.xt          # 产出 ./玄铁.exe（须在临时目录执行）
mv 玄铁.exe build/xtc_s1.exe
build/xtc_s1.exe 铁 xuantie_compiler/玄铁.xt -sc build/xtc_s2.exe
build/xtc_s2.exe 铁 xuantie_compiler/玄铁.xt -sc build/xtc_s3.exe
build/xtc_s3.exe 铁 xuantie_compiler/玄铁.xt -sc build/xtc_s4.exe

# 3. DDC：自举固定点（相邻级逐字节一致）
cmp build/xtc_s2.exe build/xtc_s3.exe   # 预期：不同（GSC 与 XTC 代码生成差异的传播）
cmp build/xtc_s3.exe build/xtc_s4.exe   # 预期：0 字节差异 ← 硬门禁

# 4. 铁铺包同步（渲染/UI 包解析依赖）
cp lib/渲染/* "$USERPROFILE/.tiepm/已安装/渲染/"
cp lib/UI/*   "$USERPROFILE/.tiepm/已安装/UI/"

# 5. 全量回归（弹窗类跳过）
python tools/regress.py --xtc build/xtc_s4.exe --skip 96_,97_,98_
```
